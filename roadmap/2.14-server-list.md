# 2.14 — The server list

The page everyone lands on, and the one that decides what the panel feels like.
Right now it is Pelican's list with the theme's colours on it. This release makes
it look like something that was designed.

## Why this first

It is the page with the most eyes on it and the most room to improve, and none of
it needs a hook that does not exist. Everything here is CSS on markup that is
already rendered, plus one toolbar injected above the table.

## What ships

### Card layouts

**Theme → Appearance → Server list** with four options:

| | |
| --- | --- |
| **Rows** | Pelican's own — one server per full-width row |
| **Cards** | A grid of cards, two or three across depending on the window |
| **Compact** | Rows at half the height, for someone running forty servers |
| **Tiles** | Cover art forward, the readings small underneath |

CSS grid on the list container, with the card's own contents reflowed. The number
of columns follows the window, and drops to one on a phone.

### Cover art that means something

Pelican already renders the egg's artwork on the card and the theme already fades
it. In **Tiles** it becomes the top of the card instead of a wash behind the
text: full width, fixed aspect, the name over a gradient so it stays readable
whatever the picture is.

A setting for how far it is dimmed, because the artwork for one game is a bright
sky and for another it is a dark cave.

### Status as a badge

The condition bar down the left is subtle to the point of being missed. An option
to render the status as a badge instead — the colour is already there in
`--bg` from Pelican's own class, so the theme does not need to know whether the
server is running, starting or dead.

Both together is also an option. Some people want the bar.

### A toolbar above the list

Injected at `panels::resource.pages.list-records.table.before`, scoped to the
server list so it appears nowhere else:

- **Filter as you type.** Client side, over the cards already on the page. Not a
  replacement for Pelican's search, which queries the server — this is for
  finding one of the twelve servers already in front of you without a round trip.
- **Layout switch.** The four layouts above, per person, remembered in their
  browser. The setting sets the default; this lets someone override it for
  themselves without touching anyone else's panel.
- **Sort.** Name, status, last used. Client side, same reasoning.

### Favourites

A star on each card, stored in the viewer's own browser. Starred servers sort to
the top.

Deliberately browser-only: it needs no table, no migration, no permission, and
nothing on the server to go wrong. Someone with three panels open sees the same
thing in each browser, and that is a fair trade for a feature that cannot break
anything.

## How

- Layouts, cover art and badges: CSS, keyed off the setting the way the card
  styles in 2.13.5 already are.
- Toolbar: a render hook returning a small Alpine component. No Livewire — it
  touches nothing on the server.
- Favourites and the per-person layout: `localStorage`, read by that same
  component.

## Risks

**The list markup is matched structurally.** The theme already reaches these
cards through `[wire\:id]:has(> .fi-color)`, which works because the card has no
class of its own. Reflowing it into a grid leans harder on that structure than
colouring it does. If Pelican changes the card, the layouts fall back to rows —
which has to be the failure mode, not a broken grid.

**Client-side filtering only sees what is loaded.** If the list paginates, the
filter finds nothing on page two. Either the filter says so plainly, or it is
only offered when everything is on one page.

## Done when

- All four layouts work at 360px, 768px and 1920px.
- Turning the theme off leaves Pelican's list exactly as it was.
- A card whose structure does not match falls back to a row rather than to a
  broken card.
- Favourites survive a page load and never reach the server.
